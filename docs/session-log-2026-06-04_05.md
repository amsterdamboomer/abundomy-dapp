## The core finding: live propagation to receivers is broken ("ghosted" requests)
Symptom: with the CID link, a request sent by Patrick does **not** appear at the receiver
without a manual refresh, so receivers never get notified → requests sit open ("ghosted").
They are not lost — they are on the primary anchor and show up on the next full reload.

**Two-peer test (decisive).** A passive Node listener with `listen: []` (non-dialable, like a
browser) connected to the Hetzner replicator and **did** receive a freshly-created request
LIVE (`⇄ LIVE update in 'proposals' (id=11)`). So the replicator's live pubsub forwarding
works even to non-dialable peers. AB's browser simply missed it.

**Root cause (proven in `@orbitdb/core/src/sync.js`).** OrbitDB v4 has two head paths:
1. **Live** = pubsub `message` → works to non-dialable peers (proven).
2. **Catch-up** = `handlePeerSubscribed` → `libp2p.dialProtocol(remotePeer, headsSyncAddress)`
   (≈ line 199): the peer that sees a new subscriber **dials** it to push heads. **A browser
   is not dialable**, so the replicator can never push missed heads to a browser.

Consequences:
- If a browser misses one live pubsub message (stale subscription / half-dead wss), there is
  no push-based recovery.
- The app's 20s safety net `resyncStores()` does `db.sync.stop()/start()` (re-subscribe),
  which only helps if the other side dials back → fails for browsers. It only re-dials the
  relay when it believes it is disconnected (`if (!connected)`), so a half-dead-but-"connected"
  socket → no action → stuck.
- **Only a full reload recovers**: a fresh node makes a NEW connection and, on connect, the
  browser dials the replicator outbound (allowed) → head exchange → catch-up.

This is exactly the relay-less problem: nobody can dial a browser to push heads, and a
pure-Kubo anchor does not speak the OrbitDB heads protocol.

## Plan going forward
### Option A (chosen) — harden live-sync on the baseline now
Make `resyncStores()` in `web/src/app.mjs` do a **browser-initiated catch-up**: instead of
relying on `sync.stop()/start()`, force a genuine fresh connection to the replicator
(hang up the existing relay connection — which clears it from OrbitDB's sync peer set via
`peer:disconnect` — then re-dial). A new connection re-triggers the outbound head exchange,
pulling any missed requests. Self-correcting: anything missed during the brief reconnect
window is caught on the next cycle. Live pubsub remains the primary fast path.

Steps:
1. Implement the reconnect-based catch-up in `resyncStores()`.
2. `npm run build:web`, then `npm run deploy` (new baseline CID).
3. Re-test with two browsers (Patrick → AB) + the Node listener: confirm AB receives the
   request within ~20s **without** a manual refresh.

### Then — relay-less redesign (the actual goal)
Use the same primitive (browser-initiated, since browsers can't be dialed):
- Keep live updates on reliable pubsub.
- For catch-up, the browser dials a dialable peer that speaks the OrbitDB heads protocol.
- A pure-Kubo anchor cannot do this, so relay-less needs one of: a pubsub head-announce that
  Kubo relays (gossipsub/floodsub interop) + bitswap for blocks, or a minimal dialable
  head-helper. Re-weigh the previously-rejected transports (circuit-relay-v2, auto-tls,
  WebRTC-Direct — see `migratieIPFSnorelay.md` §3) against this requirement.
